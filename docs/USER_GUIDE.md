# Рабочая инструкция пользователя ODE 0.21.0

Актуализировано: 2026-08-11. Инструкция описывает обычную локальную работу с
ODE. Миграционные launchers и прямое редактирование SQLite в рабочий процесс не
входят.

Если нужна короткая инструкция без технических подробностей, откройте
[`ODE_USER_GUIDE.html`](../ODE_USER_GUIDE.html) двойным щелчком или прочитайте
[`ODE_USER_GUIDE.md`](../ODE_USER_GUIDE.md). Этот документ остаётся расширенным
рабочим регламентом.

## 1. Безопасный запуск и вход

1. Запустите `start_windows.bat`, `start_macos.command` или из корня проекта
   выполните `python3 app.py`.
2. Откройте `http://127.0.0.1:8765`, если браузер не открылся автоматически.
3. Для обычной смены нажмите `Начать работу` и укажите настоящее ФИО. Этот
   локальный режим не просит пароль, но backend всегда ограничивает его правами
   инженера; ФИО используется для attribution в операциях и аудите.
4. Для управления пользователями, диагностикой и backup раскройте
   `Вход администратора` и введите логин/пароль локального пользователя.
   Простое указание ФИО административных прав не даёт.
5. На свежей установке bootstrap-администратор `lokolis` обязан сразу заменить
   начальный пароль в `Профиль`. До смены пароля остальные admin-действия
   заблокированы. При обновлении кода существующий пароль не сбрасывается.

Роли backend: `engineer` выполняет обычные рабочие операции, `viewer` только
читает, `admin` управляет административными функциями. Скрытая или видимая
кнопка сама по себе прав не предоставляет.

Сессия хранится только в запущенном процессе. Выход, перезапуск ODE или 12
часов бездействия потребуют войти заново. После пяти неверных credentialed-
входов за пять минут повторная попытка блокируется на 15 минут. Не передавайте
cookie браузера другим людям.

В ODE 0.21.0 нет входа по API-ключу, Bearer/JWT или OAuth. HTTP API использует
ту же cookie-сессию, что и браузер, и не является внешним публичным API.
Подробности для сопровождающего:
[`AUTHENTICATION_AND_API_ACCESS.md`](AUTHENTICATION_AND_API_ACCESS.md).

Надпись `ТЕСТОВЫЙ КОНТУР` означает, что запущена disposable test DB. Не
переносите из неё данные в рабочие БД. Надписи миграционного пилота или полной
кандидатной базы означают режим только для просмотра.

## 2. Выбор склада и главная навигация

При входе в `Склад` выберите `IXcellerate` или `Solar`. Это физически разные
базы: приход, расход, баланс, поставки, аудит склада и черновики одного контура
не переходят в другой. `Отпуска`, `Мониторинг`, `База знаний`, `Отчёты` и
профиль от выбранного склада не зависят.

Кнопка `ODE` возвращает на Главную. Лупа в шапке ищет позиции по S/N,
инвентарному номеру, hostname, модели, поставке, проекту, полке и другим
реквизитам. Карточка найденной позиции показывает доступный остаток, Timeline
и историю компонентов, списанных на S/N целевого оборудования.

## 3. Обычный цикл Warehouse

### Приход

1. Откройте `Склад → Приход` и выберите ручной ввод, сканер, кабели или
   приёмку из поставки.
2. Заполните дату, ответственного, тип, вендора/модель, ЦОД и полку.
3. Для оборудования и компонентов сканируйте S/N. Повторный S/N сервер
   отклонит; Inventory Number не заменяет S/N и может быть добавлен позже.
4. Один S/N принимается только как одна штука (`quantity=1`, `unit=шт`).
5. Проверьте временный список и только затем подтвердите операцию. Удаление
   одной, выбранных или всех строк до Confirm не меняет БД.

Черновик хранится локально в браузере отдельно для текущего склада и ФИО
инженера. Он никогда не восстанавливается автоматически: используйте
`Продолжить черновик`, `Начать заново` или `Удалить черновик`.

### Расход

1. Откройте `Склад → Расход`.
2. Выберите сценарий: сканер на одно оборудование, пары
   `компонент → оборудование`, поиск в балансе, кабели, CSV или ручной ввод.
3. Укажите задачу/ИЗМ и ответственного. Для целевого оборудования проверьте S/N
   и hostname.
4. До Confirm убедитесь, что источник найден и имеет положительный остаток.
   Повторное списание одного S/N и превышение остатка блокируются сервером.

Кабель обычно не имеет S/N: количество или метраж списывается FIFO из партий
прихода.

### Баланс, поставки и инвентаризация

- `Баланс` — ленивое дерево `категория → тип → вендор → модель`. Фильтры и
  экспорт работают по полной выборке, а не только по раскрытым строкам.
- `Поставки` — сначала загрузка и Preview документа, затем построчная приёмка
  сканером и закрытие поставки. Повторная приёмка уже принятого S/N запрещена.
- Простая инвентаризация сравнивает список S/N и ничего не записывает.
- Массовое назначение Inventory Number всегда выполняется как
  `Preview → проверка статусов → Confirm`; lookup идёт только по S/N.
- FULL Inventory создаёт внешний Preview и disposable candidate. Публикация в
  рабочую БД автоматически не выполняется.

### Проблемы и карточка позиции

В `Проблемы` разрешено заполнять только пустые исторические поля и отдельно
исправлять подтверждённые дубли S/N. Изменения записываются в аудит. Это не
замена сторно проведённого прихода или расхода.

Блок состава в карточке — evidence истории списаний. Он не подтверждает
фактическое текущее наличие, заводскую комплектацию или физический слот.

## 4. Остальные модули

### Отчёты и УВР

1. В `Отчёты → Отчёт за смену` заполните дату, источник, при необходимости
   номер, описание, раздел, статус, срок и комментарий. Срок обязателен для
   новой записи через интерфейс.
2. Для источника `PNR` описание и статус формируются по чек-листу. Сначала
   отмечаются зависимые подготовительные шаги; полностью закрытый чек-лист
   получает статус `Выполнено`.
3. Подвкладка `За смену` показывает все работы выбранного дня и KPI. Инженер и
   администратор могут изменить или удалить строку; viewer видит только
   просмотр. Удаление требует подтверждения.
4. Подвкладка `Все работы` содержит поиск, фильтры по датам/статусу/разделу,
   выбор строк, массовое назначение раздела и страницы по 25 записей. Фильтр
   `Только требует проверки` предназначен для разбора импортированных строк.
5. `Передача по смене` содержит только незавершённые задачи. Для PNR вместо
   уже сделанного выводятся оставшиеся действия. Выгрузка этой вкладки
   скачивает отдельный `handover.xlsx`, а не общий реестр.
6. `Экспорт в Excel` смены создаёт два листа: выполненные работы выбранного дня
   и незавершённый backlog до этой даты. Общий реестр, недельный отчёт и
   загруженный отчёт также выгружаются в XLSX.
7. CSV/XLSX импорт остаётся через Preview → Confirm. Импорт не создаёт
   складские операции; старые read-only CSV-ссылки сохранены только для
   совместимости локальных сценариев.

`Отчёты` не пишут приходы, расходы, поставки или складской баланс.

- `Мониторинг`: вставьте hostname и описание проблемы. Пробелы, табуляции и
  переносы в hostname удаляются до поиска. После явного запуска ODE получает
  доступные DCIM-поля, определяет адресатов по локальным правилам и готовит
  одинаковый девятипунктовый текст для Rooms и письма. Проверьте проект, ITSM,
  S/N, локацию, класс критичности и адресатов перед копированием. Автоматической
  отправки и скрытого запуска поиска нет. Live DCIM требует разрешённую
  браузерную сессию Microsoft Edge и optional Selenium; API-ключ в ODE для
  этого не вводится.
- `База знаний`: поиск, теги, безопасный Markdown и вложения. Редактирование
  доступно инженеру и администратору.
- `Отпуска`: общий календарь IXcellerate/Solar, графики, заявки и конфликты.
  Заявка в Сферу автоматически не отправляется.
- `Администрирование`: пользователи, аудит, диагностика и backup трёх runtime-
  БД. Restore из UI намеренно отключён.

## 5. Backup и действия при ошибке

Перед обновлением, массовым импортом или переносом создайте backup каждой
нужной runtime-БД через `Администрирование → Резервные копии`. Snapshot должен
иметь успешные SHA-256, integrity, foreign key и schema checks.

Если операция завершилась ошибкой:

1. не повторяйте Confirm много раз и не редактируйте `.db` вручную;
2. сохраните точный текст ошибки, время, выбранный склад и выполняемое действие;
3. проверьте `Администрирование → Диагностика`;
4. остановите ODE перед любыми файловыми действиями;
5. передайте сведения сопровождающему вместе с версией из интерфейса.

Для ошибок входа: `401` означает отсутствующую/истёкшую сессию, `403` —
недостаточную роль или неверный режим входа, `429` — временную блокировку после
серии неверных паролей. Не пытайтесь обходить их копированием cookie.

Полный регламент БД находится в
[`LOCAL_WORKING_DATABASE_RUNBOOK.md`](LOCAL_WORKING_DATABASE_RUNBOOK.md),
Windows-запуск — в [`README_WINDOWS.md`](../README_WINDOWS.md), а полный список
реализованных функций — в
[`project/SYSTEM_FUNCTION_MATRIX.md`](project/SYSTEM_FUNCTION_MATRIX.md).
