# Запуск ODE 0.21.1 на Windows

Это инструкция для текущего исходного кода ODE 0.21.1. Source-ZIP
`ODE_0.21.1_windows_source.zip` собирается с полным runtime closure и CRLF-
launcher; его внешний SHA-256 публикуется рядом с конкретным артефактом.
Физическая Windows-приёмка ещё не выполнена: не
выдавайте source-пакет за утверждённый рабочий rollout и всегда проверяйте
версию и внешний SHA перед распаковкой.

> **Архивы 0.21.0 отозваны для повторного переноса.** Если `cmd.exe` пишет
> `'3'`, `'cho'` или `'DE' is not recognized`, либо Python сообщает
> `ModuleNotFoundError: No module named 'baseline_rehearsal'`, остановитесь.
> Не правьте BAT/Python вручную, не переименовывайте и не заменяйте `.db`.
> Оставьте неудачную папку как read-only evidence; если в ней есть данные, не
> удаляйте её. Распакуйте 0.21.1 в **новую** папку и переносите данные только
> по проверенному checklist ниже.

Для обычного пользователя начните с красивой автономной инструкции
[`ODE_USER_GUIDE.html`](ODE_USER_GUIDE.html): она открывается двойным щелчком
в любом браузере и не требует интернета. Текстовая копия находится в
[`ODE_USER_GUIDE.md`](ODE_USER_GUIDE.md).

## Установка и обычный запуск

1. Установите Python 3.10 или новее с [python.org](https://www.python.org/) и
   включите `Add Python to PATH`.
2. Распакуйте ODE в постоянную папку, например `C:\ODE`. Не запускайте
   программу прямо из ZIP.
3. Дважды щёлкните `start_windows.bat` или выполните:

```bat
cd /d C:\ODE
py -3 app.py
```

ODE откроется на `http://127.0.0.1:8765`. Обычный `python app.py` подключает
весь рабочий контур без специальных переменных окружения:

| Модуль | Рабочая БД |
|---|---|
| Warehouse IXcellerate, Reports, Knowledge, Administration | `data\warehouse.db` |
| Warehouse Solar | `data\warehouse_solar.db` |
| Общий план отпусков | `data\vacations.db` |
| Monitoring | таблиц не имеет; локальные ignored JSON и browser history |

Физический double-click gate выполняется по
[`docs/MANUAL_TESTING_0_21_1_WINDOWS.md`](docs/MANUAL_TESTING_0_21_1_WINDOWS.md).
Пока все обязательные пункты не отмечены PASS, статус остаётся **PENDING**.

Не редактируйте, не заменяйте и не копируйте эти файлы при запущенном ODE.

## Безопасный тестовый контур

Для ручных экспериментов запускайте `start_test_windows.bat`. Launcher создаёт
или безопасно заменяет три отдельные одноразовые БД:

- `data\warehouse_test_disposable_v1.db` — демо-контур IXcellerate;
- `data\warehouse_solar_test_disposable_v1.db` — пустой Solar;
- `data\vacations_test_disposable_v1.db` — отдельный тестовый календарь.

Рабочие Warehouse-БД используются только как read-only источник согласованного
SQLite Backup API snapshot, включая committed WAL; idle source без sidecar
открывается immutable и не получает новый `-wal`/`-shm`. Рабочая Vacations DB
не читается. В интерфейсе постоянно показывается баннер `ТЕСТОВЫЙ КОНТУР`.

Каждая disposable DB содержит marker `ODE_DISPOSABLE_TEST_DB_V1`: роли
IXcellerate/Solar — `warehouse`, Vacations — `vacations`. `--overwrite`
разрешён только для уже отмеченного файла той же роли. Обычный launcher
отвергает marked test DB, а test launcher требует все три явных пути и
правильные роли. Любой `-wal`, `-shm` или `-journal` рядом с выбранной БД
блокирует startup до любой записи: сначала остановите другой процесс и
разберитесь с согласованным состоянием SQLite.

Тестовый процесс также изолирует вложения Knowledge, состояние инвентаризации,
правила Monitoring и резервные копии во временной папке. Обращение к рабочему
DCIM отключено; временная папка удаляется после остановки ODE.

Старые unmarked имена `warehouse_test_clean.db`,
`warehouse_solar_test_clean.db` и `vacations_test_clean.db` launcher 0.21.1 не
перезаписывает и не использует. Не переименовывайте их в новые `*_disposable_v1`
файлы: новые имена выбраны специально, чтобы legacy test DB не блокировали
безопасный запуск.

## Вход и права

Обычный вход создаёт сессию инженера. Администратор входит через отдельный
пункт на экране входа; право определяется session user/role, а не ФИО и не
скрытой кнопкой интерфейса. Начальный пароль новой установки сначала нужно
сменить. Пароли существующих пользователей при обновлении кода не сбрасываются.

API-key, Bearer/JWT и OAuth входа нет. Сессия хранится в памяти процесса и
передаётся только HttpOnly cookie; restart/logout и 12 часов бездействия её
завершают. Подробнее:
[`docs/AUTHENTICATION_AND_API_ACCESS.md`](docs/AUTHENTICATION_AND_API_ACCESS.md).

`start_lan_windows.bat` — legacy/dev launcher и не входит в утверждённый
source package. Не используйте его для рабочей сетевой эксплуатации: текущий
HTTP profile не имеет TLS, `Secure` cookie, persistent sessions и полноценного
server deployment. Поддержанные настройки перечислены в
[`docs/RUNTIME_CONFIGURATION.md`](docs/RUNTIME_CONFIGURATION.md).

## Резервные копии

Откройте `Администрирование → Резервные копии`. Экран показывает состояние
всех трёх runtime-БД и создаёт проверенный snapshot выбранной БД через SQLite
Backup API. Файлы сохраняются во внешнем системном каталоге, не внутри дерева
ODE. Точный путь всегда показан в UI; при необходимости его задаёт переменная
`ODE_BACKUP_DIR`.

Restore из интерфейса намеренно отключён. Имя файла и галочка подтверждения не
являются достаточной защитой от подмены рабочей БД. До реализации полного
протокола [ADR-013](docs/decisions/ADR-013-multi-database-backup-restore.md)
восстановление выполняется только как отдельная остановленная maintenance-
процедура с проверкой provenance, integrity/FK и страховочной копией.

## Основные рабочие функции

- `Склад` сначала предлагает IXcellerate или Solar; операции и остатки двух
  площадок физически изолированы.
- `Приход` поддерживает ручной ввод, сканер и CSV Preview/Confirm.
- `Расход` поддерживает сканер, выбор из баланса и CSV; целевой S/N/hostname
  фиксируется в операции.
- `Баланс` показывает ленивое дерево и позволяет открыть карточку по S/N.
- В карточке целевого сервера или коммутатора раздел `Состав оборудования`
  показывает подтверждённые историей списания компоненты, количество по типам
  и ленту операций. Схемы передней/задней панели являются обзорными: точный
  слот и заводская комплектация не выдумываются.
- `Поставки`, `Инвентаризация` и массовое назначение Inventory Number работают
  через обязательный Preview/Confirm.
- `Отчёты`, `Мониторинг`, `База знаний` и `Отпуска` — отдельные модули; они не
  используют Warehouse как скрытое хранилище своих данных.
- В `Мониторинге` вставленный hostname очищается от пробелов до поиска;
  результат включает проект/ИС, ITSM, класс критичности, адресатов и единый
  текст Rooms/письма. Поиск начинается только после нажатия кнопки. Письмо и
  Rooms-сообщение автоматически не отправляются.

Перед подтверждением массовых операций создайте backup. Повторный приход того
же S/N и повторный расход уже выданного S/N отклоняются сервером внутри
транзакции.

## CSV и Excel

Шаблоны и выгрузки используют `;` и UTF-8 BOM. Если Excel открыл файл одной
колонкой, выберите `Данные → Из текста/CSV`, UTF-8 и разделитель `;`. S/N и
Inventory Number всегда должны оставаться текстом; Excel не должен превращать
длинный серийный номер в число или экспоненту.

## Завершение работы и обновление

Закройте вкладку браузера, вернитесь в окно ODE и нажмите `Ctrl+C`. Перед
обновлением сохраните все три рабочие БД отдельно. Не распаковывайте новый ZIP
поверх рабочей папки и никогда не переносите test/candidate DB вместо runtime-
БД.

Offline migration candidate и 200-row pilot являются только воспроизводимыми
review-артефактами. Их нельзя запускать обычным launcher, помещать в `data` или
считать production-данными. Полный runbook находится в
[руководстве по локальным рабочим БД](docs/LOCAL_WORKING_DATABASE_RUNBOOK.md).
